## 1. Назначение

`doc/` — рабочая документация проекта: бэклог, архитектура, журнал решений. Корневой [README.md](../README.md) остаётся согласованным ТЗ (разделы 1–15) и **не переписывается** рабочей документацией; `doc/` дополняет его деталями, не меняя требований.

Правило приоритета при расхождении: **README → doc/ → код**. Если документ в `doc/` противоречит README, прав документ README, а `doc/` приводится в соответствие.

## 3. Правила именования

| Что | Правило | Пример |
|---|---|---|
| Основной документ | `kebab-case.md`, латиница, строчные | `architecture.md`, `content-plan.md` |
| Служебный индекс | `README.md` | `doc/README.md` |
| Бэклог | `tasks.MD` — ❗исключение: имя зафиксировано постановкой задачи, переименованию не подлежит | `doc/tasks.MD` |
| ADR | `adr/ADR-00X-краткое-имя.md`, трёхзначный номер, нумерация не переиспользуется | `adr/ADR-009-cron-warmup.md` |
| Runbook | `runbook-<процесс>.md` | `runbook-deploy.md` |
| Версионирование | Версия и дата в шапке документа; история — в разделе 6 этого файла | `**Версия:** 1.1 · **Дата:** …` |

Требования к любому документу:

1. Шапка: назначение, версия, дата, статус, связанные документы.
2. Русский язык, UTF-8, единый стиль README: таблицы вместо простыней, ❗у критичных решений, ссылки на FR-* и разделы README.
3. Mermaid: ID узлов — латиницей, подписи — в кавычках; диаграмма должна рендериться без ошибок.
4. Ссылки на код и задачи — только через ID (`T-35`, `ADR-003`), а не «тот скрипт».
5. Один документ — одна тема; больше 300 строк — повод разделить.

## 4. Куда добавлять новые документы

| Ситуация | Куда | Действие |
|---|---|---|
| Новое архитектурное или технологическое решение | [architecture.md](architecture.md), раздел ADR | Добавить ADR-00X в формате Context / Decision / Consequences и строку в раздел 8 README, если решение меняет стек |
| Новая работа по продукту | [tasks.MD](tasks.MD) | Новая задача `T-50+` или `T-C08+`, оценка, зависимости, DoD, пересчёт сметы |
| Регламент эксплуатации (деплой, откат, пробуждение проекта) | `runbook-<процесс>.md` + строка в разделе 2 | Создать документ, сослаться на него из tasks.MD 7.2 |
| Исследование или сравнение вариантов | `adr/ADR-00X-*.md` + строка в разделе 2 | Решение всё равно фиксируется в architecture.md |
| Контент-план, тексты, инструкции | Вне `doc/`: контент живёт в БД и Storage | В `doc/` — только правила и чек-листы (tasks.MD 7.1) |
| Скриншоты, PDF, `.glb`, видео | ❌ не в `doc/` | Хранятся в Storage или `public/`; в документах — ссылки |

Новый документ считается существующим, только если он: (1) лежит в `doc/`, (2) добавлен в таблицу раздела 2, (3) имеет шапку и статус.

## 5. Статусы и жизненный цикл

1. 🟡 **draft** — документ написан «для себя», ссылаться на него нельзя.
2. 🔵 **review** — проверен на соответствие README и задачи; ждёт решения владельца продукта.
3. ✅ **approved** — источник истины; изменение только с новой версией и записью в журнале.
4. ⛔ **superseded** — заменён; в шапке указывается ссылка на замену, файл не удаляется.

Владелец документации — один разработчик (он же владелец продукта в учебном MVP): отдельной роли техписателя нет, поэтому «согласование» — это сверка с README и прогон чек-листа приёмки.
